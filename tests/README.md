## 어디서 왔나

케이스를 손으로 지어내지 않았다. **한국관광공사 API 실측값에서 뽑았다.**

| 코퍼스 | 규모 | 쓰인 곳 |
|---|---|---|
| `acmpyPsblCpam` (동반가능동물) | 149종 | parseRules |
| `acmpyNeedMtr` (필요사항) | 28종 | parseRules |
| `etcAcmpyInfo` (기타정보) | 60종 | parseRules · zoneHint |
| `restdate` (휴무일) | 42종 | openHours |

기대값은 **두 명의 검증자가 소스를 각각 따라가 계산한 뒤 서로 동의한 것만** 남겼다.
한 명은 정규식과 분기를 손으로 실행했고, 다른 한 명은 "이 값이 맞다면 사용자가
헛걸음하거나 갈 수 있는 곳을 못 가게 되는가"를 따졌다. 이견이 있던 11건은 뺐다.

## 실패는 사용자 피해다

이 서비스는 "모호한 출입 조건 때문에 현장에서 거부당하는 헛걸음"을 막으려고 만들었다.
판정이 틀리면 두 방향 모두 실제 피해가 된다.

```
🔴 못 가는데 '입장 가능'  → 헛걸음. 이 서비스의 존재 이유가 무너진다
🟡 갈 수 있는데 '불가'    → 기회 손실. 사용자는 틀렸다는 걸 영영 모른다
```

그래서 테스트 이름과 주석에 **어느 방향의 피해인지**를 적어뒀다. 실패하면
"정규식이 안 맞는다"가 아니라 "누가 어떤 헛걸음을 하게 되는가"로 읽어야 한다.

## 새 케이스를 추가할 때

지어내지 말고 실데이터에서 가져와라.

```bash
# 실제 저장된 원본 보기
jq -r '.rules | to_entries | .[0:5][] | .value.raw' data/petRules.json

# 특정 표현이 실제로 몇 건이나 있는지
jq -r '[.rules[]|select(.!=null)|.raw.acmpyPsblCpam]|group_by(.)|map({v:.[0],n:length})|sort_by(-.n)[]|"\(.n)\t\(.v)"' data/petRules.json
```
